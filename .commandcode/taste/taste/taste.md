# Taste
- Prefers an investigation-first approach: understand how something currently works and identify the root cause of inconsistency/issues before proposing changes. Confidence: 0.5
- Asks for a recommended "best solution" (a diagnosis plus proposed approach) before committing to an implementation. Confidence: 0.45
- Once a plan is proposed, approves it tersely (a single word or short imperative like "proceed" / "push now", or echoing the agent's own phrasing) and expects the agent to carry the change through end-to-end — implementation, tests, and verification — without step-by-step check-ins. When asked to choose between an action and a precaution (e.g. push the tag vs. set up guardrails first), picks the action. Confidence: 0.6
- Before a release/submission, wants the work re-verified against the platform's official requirements (and expects the agent to check the authoritative source itself), plus concrete step-by-step instructions for how to publish/submit. Asks "how is the process?" and expects the canonical procedure laid out in ordered phases (one-time submission/review vs. every subsequent release), with exact copy-pasteable commands and the order-of-operations/failure modes called out — automation offered only as a separate optional step. Confidence: 0.55
- Reports failures as terse, context-free one-liners or by pasting raw machine/third-party error output verbatim (e.g. "critical error on activation", a full automated scan/validation failure dump) and expects the agent to locate the root cause itself from the codebase, tooling source, and platform rules rather than ask for logs or reproduction steps up front. Confidence: 0.6
- Before choosing an approach to shipping/distributing software, asks for the canonical "best practice" and wants the trade-offs laid out (including simply following the platform's official channel) rather than accepting a custom workaround. Confidence: 0.4
- Scopes new feature ideas by asking a blunt feasibility question ("can we add X? complex?") and expects a complexity/cost breakdown per target, the real blockers, an explicit "skip this" recommendation, and a phased sequence (abstraction/refactor first, then additive value) rather than jumping straight into implementation. Confidence: 0.45
- Wants the factual premises behind a recommendation verified against the real environment before committing to an approach or to public-facing copy that depends on them (e.g. "check if the current repo is public or private", "we have only GitHub integration right?"). Includes their own beliefs offered as assumptions to be checked and corrected ("i think i have blocked all already) can you check?"). Such checks should be grounded in the actual code/tests/live settings, not assumed. Confidence: 0.6
- When asking to "check" work before shipping, expects a proactive completeness audit — not just a verdict on what was submitted, but an explicit list of everything still missing or blocking (missing required artifacts, build scripts that would clobber the new work, stray files that would get packaged, missing tags), each item concrete and actionable. Confidence: 0.5
- Asks how a cross-cutting concern is "threaded" through the project (e.g. the version number) and wants the current mechanism laid out in full: every place the value is duplicated, which copy is authoritative, and what breaks when they diverge — preferring a single source of truth that the build enforces over hand-maintained copies. Expects the agent to bump the version itself when a change warrants it ("bump version if needed") instead of waiting to be told, and will check up on it ("have you bumped version?") when it was left unchanged. Confidence: 0.6
- Wants release/distribution artifacts (downloadable zip named after the current version) produced automatically by CI on commit/push rather than by manual local build-and-tag steps; manual release procedures are treated as a defect. Confidence: 0.5
- Cares about the public-facing presentation of the product, on the repo and inside the end-user UI: README polish such as a banner image in the heading (plugin-directory style assets), brand icon surfaced in the WordPress admin Updates screen (and expects the asset already committed to the repo to be reused rather than a new one generated), and notices/cares about aggregate repo metadata like the language-percentage breakdown showing stray tooling languages — when a stray-language script shows up, prefers deleting the script outright (along with the build flags, docs, and references that depend on it) over a cosmetic suppression such as `.gitattributes` linguist rules, keeping the project to its core language plus one build script. Confidence: 0.5
- Prefers to own the release/distribution channel: ship updates from their own GitHub Releases (WordPress `Update URI`) rather than depend on the WordPress.org directory, and wants the product's own self-update to work that way too — accepting the loss of directory listing as a fair trade. Confidence: 0.45
- Expects the agent to drive the git/GitHub lifecycle hands-on end-to-end — diagnose why a commit/push isn't landing, fix the underlying repo/.git hygiene problem, then commit, branch, push, open the PR, and merge (and clean up ignore rules / untrack junk while there) — rather than leaving changes uncommitted in the working tree. Confidence: 0.45
- Code must honor the project's declared minimum PHP version (7.4): avoid PHP 8.0+ only syntax such as union types, and validate against the target PHP version rather than assuming the CLI default. Confidence: 0.5
- Wants CI actually green: failing lint/quality checks are to be fixed at the source (docblocks, formatting, annotations for intentional violations) and then enforced as required status checks — not worked around by dropping the failing job from the pipeline or merging past red. Confidence: 0.55
- Cares about release integrity and access control: wants branch/tag/release-environment protections verified and tightened so that only they can merge to the default branch, create release tags, or publish, with admin bypass closed. Expects the agent to inspect the live rulesets/environments/collaborators and state plainly where the actual protection is weaker than they assumed. Confidence: 0.5
- Requests a release as one terse line ("bump to new version, push and merge in main and create release") and expects the whole chain completed unattended: bump the version everywhere it's duplicated (header, constant, stable tag, POT metadata, test bootstrap), write the changelog + upgrade notice entries, build, run checks, open and merge the PR, push the tag, and self-approve the release deployment through to a published GitHub release with the downloadable zip — no confirmation prompts at the merge/tag/approval gates. Confidence: 0.5
- Prefers incremental, "progressive" shipping: when merged work is sitting unreleased, wants a small patch version cut right away ("cut 1.0.2 please so is progressive") rather than batching it into a later, larger release. Confidence: 0.45
- Cares about dependency/toolchain freshness: when a deprecation or outdated-dependency warning surfaces (e.g. CI actions on a deprecated runtime), wants it fixed now by bumping to the current major ("bump so we are updated") rather than filed as a follow-up — and would rather land one clean PR that advances everything than a minimal targeted patch. Confidence: 0.5
- Batches several unrelated questions and tasks into a single terse message and expects every item answered explicitly (question-by-question, with a separate summary of what was changed) while the agent goes ahead and performs the actions in parallel. Confidence: 0.45
